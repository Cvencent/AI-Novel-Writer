# 长短两层大纲与连贯性架构设计

日期：2026-10-20
状态：待作者评审
范围：AI 小说作家（书童 Pagekin）的架构阶段、大纲生成、连贯性数据与生成可观测性

## 1. 背景

当前创作链路：

    设定 → 架构（前提／角色／世界观／情节大纲）→ 蓝图（逐章）→ 正文

其中「情节大纲」是**逐章一段**的细纲，写入 `project_core.synopsis`。它必须连续生成到全书总章数才算确认，中途没有作者确认卡点。

## 2. 实测问题

### 2.1 大纲走偏且无法干预

作者项目《源起》：都市玄幻开局，第 150 章后逐步漂移为市井谍战。

抽样第 5 / 60 / 150 / 250 / 320 / 400 / 460 / 500 / 508 章，第 150 章起出现高度重复的章节模板：

    清晨对账 → 陈砚念旧账／林越补两条遗忘 → 钟厥七点前蹲点 → 回报线索 → 匿名记录提示

第 150 到第 508 章，350+ 章沿用同一结构，人物退化为功能符号，题材漂移。

根因是三条架构缺陷：

1. **单层结构**：没有「先看全局、再落细节」的层次；方向一旦写偏，无法回头修正。
2. **无分段确认**：工作流一路跑到底，作者只能在事前写提示词或事后整段重生成。
3. **只有压缩文本**：生成第 N 章时，模型对前文的全部认知是一段压缩字符串，没有结构化记忆。

### 2.2 连贯性零件齐全但未接线

作者项目只读实测：

| 表／字段 | 设计用途 | 实际 |
|---|---|---|
| `summary_snapshots` | 每章结构化摘要 | 0 行 |
| `narrative_thread_plans` | 线索／伏笔生命周期 | 0 行 |
| `narrative_thread_confirmations` | 线索推进事件 | 0 行 |
| `characters.cs_*` | 角色当前状态 | 全空 |
| `plot_tree_snapshot` | 情节树 | 0 长度 |
| `character_states` | 全局角色状态 | 0 长度 |
| `blueprints` | 逐章结构化蓝图 | 0 行 |

表已存在，写入路径（`SummaryRepository.saveSnapshot`、`NarrativeThreadRepository.createPlan／confirmEvent`）也已存在，但情节大纲工作流只读写 `project_core.synopsis`，未接入任何一项。

### 2.3 生成过程不可观测

生成时「AI 输出」只有流式正文。作者看不到模型查了哪些章节、人物、线索，无法判断结论是否有据。

## 3. 目标

1. 大纲拆成「粗纲／细纲」两层：粗纲管方向，细纲管落章。
2. 粗纲按自然段落划分，段长可变（约 30–200 章），由内容需要决定，不固定批大小。
3. 粗纲阶段不出现具体人名，只描述剧情走向；人名与角色在细纲阶段才出现。
4. 两层都可对话式修改：改某一段，或从某章之后全部重新生成；改动按规则向下传递。
5. 接入既有连贯性零件，让生成时有结构化记忆，而非只有压缩文本。
6. 生成过程可观测：应用内新增日志页，可查看每次模型调用的完整 Prompt、完整返回与工具调用，默认折叠。
7. 验证改为轻量方式：在《源起》上每项功能验证一两次，另新建一部 30–50 章短测试小说走通完整链路。不做存量回填。

## 4. 非目标

- 不重写蓝图与正文工作流（保持现有 `blueprints` → 章节写作链路）。
- 不改变 `project_core.synopsis` 作为细纲载体的事实（粗纲使用独立存储）。
- 不引入外部依赖或云端服务。
- 不自动改写既有 508 章正文。

## 5. 设计概览

### 5.1 新链路

    设定（前提／世界观）
      → 粗纲（Arc Outline，分段、无人名）
      → 细纲（Chapter Outline，逐章一段，含人名）＝ 原「情节大纲」
      → 蓝图（逐章结构化）
      → 正文

角色名单不再是大纲生成的前置阻塞项：粗纲不依赖角色；细纲生成时按需生成／合并角色。

### 5.2 两层职责

| | 粗纲 | 细纲 |
|---|---|---|
| 粒度 | 一段覆盖 N 章（N 可变） | 一章一段 |
| 人名 | 禁止出现 | 必须出现 |
| 内容 | 事件链、冲突、转折、结果、节奏与情绪走向 | 本章人物、行动、阻力、结果、钩子 |
| 作用 | 锁定题材与走向，防漂移 | 可直接落成蓝图与正文 |
| 确认 | 逐段确认 | 逐段确认（按粗纲段） |

## 6. 数据模型

### 6.1 新增表 `arc_outlines`

| 字段 | 类型 | 说明 |
|---|---|---|
| id | INTEGER | 主键 |
| arc_index | INTEGER | 段序号，从 1 起 |
| from_chapter | INTEGER | 起始章（含） |
| to_chapter | INTEGER | 结束章（含） |
| title | TEXT | 段标题 |
| summary | TEXT | 粗纲正文（不含人名） |
| beat | TEXT | 段落功能标签，用于形态去重 |
| status | TEXT | draft \| confirmed \| needs_regen |
| revision | INTEGER | 修订号，每次编辑 +1 |
| created_at | TEXT | |
| updated_at | TEXT | |

约束：同项目内区间不重叠、连续覆盖，从第 1 章开始。

### 6.2 新增表 `outline_segment_bindings`

| 字段 | 类型 | 说明 |
|---|---|---|
| chapter_number | INTEGER | 章号（主键） |
| arc_id | INTEGER | 所属粗纲段 |
| arc_revision_at_build | INTEGER | 生成该章细纲时的粗纲修订号 |
| fine_state | TEXT | fresh \| stale |

判定：`arc.revision > binding.arc_revision_at_build` → 该章细纲标记 `stale`。

### 6.3 连贯性数据（复用既有表）

- `summary_snapshots`：每章结构化摘要，写入既有列 `chapter_notes`／`character_states`／`continuity_facts`。
- `narrative_thread_plans` ＋ `narrative_thread_confirmations`：线索生命周期（埋设／推进／回收）。
- `characters.cs_*`：角色当前状态（位置、能力、身体、心理、关键物品、最近事件、更新章）。

### 6.4 迁移与兼容

- 新表经既有 migration runner 增量创建，不改 `project_core`。
- 既有项目无粗纲时：`project_core.synopsis` 仍作为细纲可读可写，粗纲区显示「未建立」，并提供「从现有细纲反推粗纲」入口。
- 细纲原有 CAS 校验（`synopsis_db_hash`、`synopsis_facts_fingerprint`）保持不变。
- 粗纲改动不直接改写 `synopsis`，只把受影响章节标记 `stale`。

## 7. 粗纲规格

### 7.1 分段

- **段长由模型判断**：模型依据该段的戏剧命题本身决定跨度——命题大就切长段，命题小就切短段。系统只给一个允许区间（默认 20–200 章）作为边界，不预设固定大小，也不按批次数切分。
- AI 先提出分段方案（每段：起止章、该段戏剧任务、beat 形态标签、以及为何是这一跨度），作者可增删改边界。
- beat 标签由模型在生成该段时给出，取自固定小集合（铺垫／升级／逆转／低谷／高潮／余波／过渡），作者可改。
- 每段生成后由作者选择**继续方式**（页面上是两个按钮，可随时切换）：
  - **等我确认**：停下，作者看过并确认后才生成下一段。用于前期摸索方向。
  - **跳过确认**：连续生成后续各段，不再逐段停下。用于方向已经稳定、想快速铺完。
- 两种模式随时可切换；切换为「跳过确认」后仍可随时暂停回到逐段确认。
- 未确认段保持 `draft`，可反复重生成。

### 7.2 内容约束（写入提示词并校验）

粗纲每段只描述：

- 主要事件链与因果关系
- 冲突与代价
- 转折点与节奏（加速／放缓／高潮／余波）
- 结果与状态变化（世界层面，不落到具体人名）
- 情绪基调走向

必须禁止：

- 任何具体人名（以 `characters` 名单匹配校验）
- 逐章流水账

### 7.3 形态去重

生成新段时注入已完成段的 `beat` 标签，要求新段不得复用同一节奏形态。校验：若新段与最近 K 段 `beat` 完全相同，判不合格并要求重写。

## 8. 细纲规格

- 粒度：一章一段，格式 `## 第N章：标题` ＋ 正文。
- 生成范围：以一个已确认粗纲段为单位。
- 注入上下文（固定预算，不随总章数增长）：
  - 本段粗纲全文
  - 相邻段粗纲摘要（前段结尾、后段开头）
  - 最近 3–5 章细纲全文
  - 本段涉及人物的角色卡与最近状态
  - 活跃线索（埋设与待回收）
  - 最近章节摘要的检索结果
- 人名：本章人物优先取自现有角色名单；若剧情确需新人物，先作为候选加入名单（作者确认或按自动化规则合并）再写入细纲。角色可以边写细纲边追加。

## 9. 修改与传递规则

### 9.1 粗纲层修改

作者改动第 i 段后：

1. 该段 `revision + 1`，`status` 置 `confirmed`（若作者确认）。
2. 该段覆盖章节的 `fine_state` 置 `stale`。
3. 界面提示「第 X–Y 章细纲与粗纲不符，需要重生成」，提供「立即重生成」与「稍后处理」。
4. 依赖被改段结果的后续段，一并标记 `needs_regen`。

### 9.2 细纲层修改

作者改动第 N 章后：

1. 仅更新该章，`fine_state` 置 `fresh`，不动粗纲。
2. **作者的手动编辑即为权威**，直接保留，不弹窗、不追问。
3. 若该章与所属粗纲段出现偏差，模型在后续生成相邻章节时自行对齐（以作者的编辑为准），偏差只记录进诊断与漂移报告，不打断作者。

### 9.3 对话式修改

「改第 N 段」与「从第 X 章之后全部重来」走同一条对话式入口：

- 作者用自然语言说明方向（例：「第 150 章之后不要走谍战，拉回学院线和源核阶位」）。
- 系统确定影响范围（段级或章级），展示受影响章节清单。
- 确认后重生成，按 9.1／9.2 规则传递。
- 重生成前自动把被覆盖内容存为可恢复版本。
- 全程不弹出「与粗纲冲突」这类询问；偏差由模型处理并记入诊断。

## 10. 连贯性机制

### 10.1 章节摘要

每章细纲确认后（以及正文定稿后）生成结构化摘要写入 `summary_snapshots`：

    章号 / 剧情摘要（3–5 句）/ 出场人物 / 地点 / 时间点
    / 推进的线索 / 状态变化 / 新增事实

细纲层摘要与定稿层摘要分列保存，互不覆盖。

### 10.2 线索生命周期

- 从粗纲段与细纲章节抽取线索，写入 `narrative_thread_plans`。
- 埋设／推进／回收分别写 `narrative_thread_confirmations`。
- 生成细纲时强制注入「活跃线索」与「临近到期线索」。
- 长期未推进的线索在界面告警。

### 10.3 角色状态

- 每个出场角色的位置、能力、身体、心理、关键物品、最近事件。
- 更新来源：细纲确认（预测）与正文定稿（实际），后者优先。
- 生成新细纲时注入相关角色的最近状态。

### 10.4 知识边界

- 每个角色维护「知道／不知道／误以为」三类事实。
- 生成时校验叙述是否泄露角色不应知道的信息。

### 10.5 一致性校验

生成与定稿后运行：

- 规则校验：已退场／死亡角色再出场、物品位置冲突、时间线倒退、章节编号跳空、人物不在名单。
- 形态校验：与最近 K 章结构重复（治 2.1 的模板化）。
- 结果写入既有 `consistency_exemptions` 支持作者豁免。

## 11. 生成过程可观测：日志页

### 11.1 现状（已核实）

模型调用的完整 Prompt **已经持久化在数据库中**，只是没有界面读取入口：

- `generation_attempts.usage_receipt_json` 内含 `replayTask.messages`，保存了该次调用的完整系统提示词与用户提示词。
- `generation_artifacts.artifact_json` 保存该次调用产出的完整文本（含部分产出）。
- 两条记录通过 `attempt_id` 一一对应。

也就是说，日志能力**不需要新建采集管道**，只需要新增只读投影与界面。

### 11.2 新增日志页

在应用内新增一个「日志」入口（位于设置附近或独立标签），面向排查使用，包含三个视图：

**视图一 · 调用列表**

按时间倒序列出每一次模型调用，每行显示：

    时间 / 阶段（如「细纲 第151章」）/ 模型 / 状态 / 耗时 / 输入 tokens / 输出 tokens

可筛选：按阶段、按状态（成功／失败）、按时间范围、按关键词。

**视图二 · 单次调用详情**（点击某一行展开）

- **完整 Prompt**：系统提示词与用户提示词逐条展示，可复制、可全文搜索。
- **完整返回**：该次调用的原始输出文本。
- **元信息**：模型、阶段、耗时、tokens、结束原因（stop／length）、失败码。
- **工具调用**：该次调用中模型发起的检索工具调用，逐条列出工具名、参数、返回条数与摘要，可展开看全文。

默认全部折叠，点击展开；提供「复制本次调用」把 Prompt 与返回一起拷出。

**视图三 · 工具调用汇总**

把一次工作流内的所有工具调用按顺序串起来：

    调用 7 次工具
      ▸ search_outline    query="断头巷 林越"  topK=5   → 返回 5 条
      ▸ read_character    name="林越"              → 返回角色卡 1 条
      ▸ read_threads      chapter=151               → 返回活跃线索 3 条

### 11.3 数据投影

新增只读 IPC：`logs:list-calls`（分页列表）与 `logs:read-call`（单次详情）。

实现上复用既有 `generation_attempts` 与 `generation_artifacts`，不新建写入路径；必要时补充按 run／阶段检索的索引。**不写入任何新的事实来源。**

### 11.4 隐私边界

- 日志仅在本地读取与展示，不上传。
- 展示前对模型密钥等凭据做脱敏；正文与提示词保持原样（作者需要看的就是它们）。
- 提供「清空日志」入口。

### 11.5 大纲生成的检索工具

为大纲生成接入只读检索工具（复用 `src/services/agent/tools` 既有实现与 `search-knowledge`）：

- `search_outline`：按关键词／语义检索已确认章节
- `read_chapter_summary`：读某章结构化摘要
- `read_character` / `list_characters`
- `read_threads`：读活跃线索
- `read_worldbuilding`

这些调用连同参数与返回，记录进视图一／二的「工具调用」区与视图三。

## 12. 验证方式

两条验证线，都是**轻量**的——每个功能只验证一到两次，不追求长跑。

### 12.1 线一：在《源起》上做轻量验证

直接在作者现有项目《源起》上操作，**不改动第 1–508 章正文**：

1. 从现有细纲反推一两个粗纲段（例如第 470–508 章），验证反推结果可用。
2. 对其中一个段执行一次「重生成」与一次「对话式改造」，验证改动传递与影响范围圈定。
3. 对两三章执行一次摘要／线索／角色状态写入，验证连贯性接线真实落表。
4. 打开日志页，验证能看到这几次调用的完整 Prompt 与返回，以及工具调用列表。

每项功能验证一至两次即可，不做长跑，不触发大批量生成。

### 12.2 线二：新建一部短测试小说

新架构实现完成后，由 AI 在本地新建一部**短篇测试小说（30–50 章）**，走一遍完整链路：

1. 新建项目，设定总章数（30–50 章）与题材。
2. 生成粗纲：验证分段由模型判断、段长落在允许区间、**全文无人名**、beat 形态不重复。
3. 切换「等我确认」与「跳过确认」两种模式各一次，验证行为符合预期。
4. 生成细纲：验证逐章一段、人名来自角色名单、上下文预算恒定。
5. 验证连贯性落表：`summary_snapshots` / `narrative_thread_plans` / `characters.cs_*` 有真实数据。
6. 验证修改传递：改粗纲段 → 对应细纲标 `stale`；改细纲章 → 不弹窗、直接保留。
7. 验证对话式改造：「从第 X 章之后重来」能正确圈定范围并重生成。
8. 打开日志页，验证完整 Prompt、返回、工具调用三者齐全。

**测试小说控制在 30–50 章，不写长**。目的只是确认功能正确，不是产出作品。完成后保留为回归用例。

### 12.3 不做的事

- **不对《源起》做存量回填**：508 章的数据保持现状，不批量补摘要／线索。
- **不跑长链路**：不做几百章连续生成的验证。

存量回填能力按原设计保留为**延后能力**（阶段 6），需要时再单独评估。

## 13. 测试策略

- 单元：粗纲人名校验、段区间连续性与不重叠、修订号与陈旧判定、传递规则、形态去重。
- 集成：粗纲段确认 → 细纲生成 → 摘要落库 → 线索写入 → 检索命中；改粗纲 → 对应细纲标记 stale。
- 真实链路：作者项目 508 章回填在本地跑通，验证摘要数、线索数、检索命中。
- 回归：现有情节大纲批次状态机、CAS 校验、恢复稿、连续生成测试全部保持通过。
- 性能：3000 章规模下上下文预算恒定（扩展既有 `buildOutlineRetrievalContext` 测试）。

## 14. 分期落地

- 阶段 1：数据模型与迁移；粗纲存储与编辑；两层链路打通（粗纲 → 细纲）。
- 阶段 2：修改与传递规则；对话式改段／改章。
- 阶段 3：连贯性接线（摘要、线索、角色状态、知识边界、一致性校验）。
- 阶段 4：生成过程工具调用可观测。
- 阶段 4：日志页（调用列表、单次详情、工具汇总）。
- 阶段 5：《源起》轻量验证 + 新建 30–50 章测试小说端到端验收，形成回归用例。
- 阶段 6（延后，非本阶段）：存量项目回填与漂移报告。

每阶段独立可验证、可发布。实施需拆成多份计划。

## 15. 风险

- 粗纲段长由模型判断，可能出现跨度不合理；作者可随时改边界，且允许区间设上下限兜底。
- 改名／合并角色会影响既有大纲人名一致性，由模型按名单归一，历史偏差记入诊断。
- 粗纲修订会让大批细纲变 stale，需要清晰的重生成成本提示。
