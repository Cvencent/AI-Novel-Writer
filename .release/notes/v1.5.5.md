# 1.5.5

## 中文

这一版解决「作品写大之后越来越卡」的根因。

### 运行列表不再把整部作品的生成记录读一遍

- 打开过《源起》（477MB，201 个历史运行、743 条生成记录）会发现切页很卡。实测：切到「蓝图」要等 4.4 秒，其中 **`generation:list` 一次就花 2.6 秒**。
- 原因是这个接口名义上是「列表」，实际却对**每一个**历史运行都做了一次完整水合：读它整份运行绑定（100MB）、把该根下所有生成尝试的记录读出来并解析（353MB）、重拼可见正文、再算一遍哈希。而调用方要的只是「这是哪个运行、做什么的、什么状态」。
- 现在列表改成**一次投影查询**：运行 id、根 id、操作名、状态都由 SQLite 直接从 JSON 里取，不再把绑定或生成记录搬进内存。完整视图仍然按需读取（`generation:read`），需要它的人一点没少拿。
- 实测同一部作品：**`generation:list` 2552ms → 116ms**（快 22 倍），查询计划里不再出现那张 355MB 的表。

### 切页不再重复读几十次恢复上下文

- 「蓝图」「正文」「设定」每切一次，界面会读 9～30 次 `generation:read-context`，每次都要把一个运行完整水合一遍——合计 2.7 秒，而其中**真正需要恢复的只有 1 个**。
- 根因有两处：蓝图恢复会遍历**所有**运行去问「你有没有蓝图恢复稿」；运行侧页也会对所有运行读一遍恢复上下文。
- 现在先用列表里的 `operation` 把范围缩小（蓝图恢复只可能挂在目录蓝图任务上），再对候选逐个读。**实测这三页的 `read-context` 调用从 9～30 次降到 0 次。**

### 恢复上下文内部不再重复水合

- `read-context` 会对同一个运行走三段（大纲进度、规划续写、恢复稿），每段各自把该运行的全部尝试读一遍并解析。
- 其中两处其实只需要一个字段：一次读整个运行的记录只为取一个 `purpose` 枚举值，一次读整份大纲只为拼恢复稿的候选文本。现在都改成让 SQLite 只投影出真正需要的列。
- 恢复稿的候选文本仍然保持原来的取舍：**内存中本次会话刚流出的候选优先于库里的旧快照**；只是不再为此把整份账本重建一遍。

### 实测（《源起》只读副本，工作树构建）

| 操作 | 修复前 | 修复后 |
| --- | --- | --- |
| 切「蓝图」 | 4353ms | **1671ms** |
| 切「正文」 | 2766ms | **1529ms** |
| 切「设定」 | 2366ms | **1590ms** |
| `generation:list` | 2552ms | **116ms** |
| 「蓝图/正文/设定」的 `read-context` | 9～30 次 | **0 次** |

### 验证

- 浏览器测试 78 文件 / 940 项全过；生成与运行相关的 Node 测试 872 项通过（另有 1 项既有失败与本版无关，在改动前的干净版本上同样失败）。
- 新增一条性能回归防线：用《源起》实测副本断言「运行列表的查询计划不得触碰生成记录表」，并且列表耗时至少比逐运行水合快 5 倍。库不存在时自动跳过。
- 类型检查、lint、i18n 检查通过。

升级不改动作品数据。

Windows 安装包未签名，系统可能提示未知发布者。

## English

This release fixes the root cause of "the more I write, the slower it gets".

### The run list no longer reads the whole book's generation log

- On 源起 (477 MB, 201 historical runs, 743 generation records) switching pages was slow: opening the Blueprint page took 4.4 s, of which **a single `generation:list` call was 2.6 s**.
- The interface was named "list" but hydrated **every** historical run in full: its whole run binding (100 MB), every generation attempt under that root read and parsed (353 MB), the visible text re-concatenated, and hashes recomputed. Callers only wanted to know which run it is, what it does, and what state it is in.
- It is now **one projection query**: run id, root id, operation and status are extracted from JSON by SQLite. Full views are still read on demand (`generation:read`), so nothing that needs them loses them.
- Measured on the same book: **`generation:list` 2552 ms to 116 ms** (22x), and the query plan no longer touches the 355 MB attempt table.

### Switching pages no longer re-reads recovery context dozens of times

- Every visit to Blueprint / Manuscript / Setup issued 9-30 `generation:read-context` calls, each hydrating a whole run - 2.7 s in total, while **only 1 run actually needed recovery**.
- Two causes: blueprint recovery asked *every* run whether it had a recovery draft, and the run sheet read recovery context for every run.
- Both now narrow the set first using `operation` from the list, then read only the candidates. **Those calls went from 9-30 per page visit to 0.**

### Recovery context no longer re-hydrates itself

- `read-context` walks three stages of the same run (outline progress, planning continuation, recovery draft), each re-reading and re-parsing that run's attempts.
- Two of them needed exactly one field: one read an entire run's records to get a single `purpose` enum, another read a whole outline to build the recovery draft's candidate text. Both now let SQLite project only the columns actually used.
- Candidate selection keeps the original preference: an in-memory candidate from this session wins over an older stored snapshot - it just no longer rebinds the whole ledger to find it.

### Measured (read-only copy of 源起, worktree build)

| Action | Before | After |
| --- | --- | --- |
| Open Blueprint | 4353 ms | **1671 ms** |
| Open Manuscript | 2766 ms | **1529 ms** |
| Open Setup | 2366 ms | **1590 ms** |
| `generation:list` | 2552 ms | **116 ms** |
| `read-context` on those pages | 9-30 calls | **0 calls** |

### Verification

- 78 browser test files / 940 tests pass; 872 generation and run related Node tests pass (one pre-existing failure is unrelated to this release and fails identically on clean pre-change code).
- A new performance regression guard asserts, against a real 源起 copy, that the run list's query plan never touches the attempt table and that it is at least 5x faster than per-run hydration. It skips when the database is absent.
- Typecheck, lint and i18n checks pass.

Upgrading does not touch project data.

The Windows installer is not code-signed; Windows may warn about an unknown publisher.
